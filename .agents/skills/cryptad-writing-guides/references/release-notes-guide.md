# Release notes style guide

This document defines the rules and conventions for Cryptad release notes.

Prerequisite: read `writing-guide.md` first.

## Source of truth

- Cryptad publishes authoritative release notes on GitHub Releases.
- When changelog artifacts are requested, maintain repo-root `changelog-full.md`,
  `changelog-short.txt`, and `changelog-full.txt` together. A release-body-only request does not
  require creating these files.
- Release tags use integer build numbers: `v<build-number>`.
- Render release names with the same prefix in prose and headings: `Cryptad v<build-number>`, not `Cryptad <build-number>`.
- Each build gets its own release body. Do not design the notes around semver minor/patch files.
- For pre-tag drafting, retain the selected candidate: `release/<build-number>` for ordinary
  stabilization, `hotfix/<build-number>` for a hotfix, or an explicit user-selected ref. Follow
  [source selection and range validation](../../cryptad-write-release-notes/references/drafting.md)
  and use the same resolved commit throughout drafting and verification.

## Stable 1.0 generated notes

Stable 1.0 keeps its product/API milestone name while retaining the integer build/tag model. Use
`Stable 1.0` together with `build <build-number>` and `v<build-number>`; do not introduce a
`1.0.0` project version or tag.

The Stable RC and GA note files are generated release artifacts, not independent hand-written
changelogs:

- `stable-rc` renders `docs/templates/stable-1.0-rc-release-notes.md` from the authenticated freeze.
- `stable-ga` renders `docs/templates/stable-1.0-ga-release-notes.md` from the authenticated RC,
  post-freeze validation, authorization, exact limitations, and maintenance baseline.
- `stable-maintenance` renders `docs/templates/stable-1.0-maintenance-release-notes.md` from the
  authenticated GA root, latest predecessor, frozen integer-build candidate, compatibility delta,
  evidence, package/updater state, limitations delta, and release class.
- Required template tokens have a fixed order and cardinality. Missing, duplicated, unknown, or
  reordered tokens are release blockers.
- Before verified publication, do not claim that the tag, GitHub Release, update descriptor,
  catalog publication, or network insert exists. Publication state belongs in the separate receipt.
- Escape untrusted Markdown text and link destinations. Frozen limitation/support metadata must
  render as literal audited text, not active injected headings, links, or images.
- Publish only the planned public assets. The public checksum file must not reference internal
  authorization, validation, redaction, or input files that are absent from the Release assets.
- Maintenance notes must describe a shortened hotfix window and its outstanding follow-up
  obligation accurately. Do not claim closure until the side-effect-free closure record is
  authenticated through the current successor lineage.
- Preserve the generated note digest through protected publication and verify it in the receipt.

When the template needs editorial changes, edit the checked-in template and rerun the command.
Never patch generated notes inside a release workspace.

## Audience split

- `changelog-full.md`: Markdown changelog for non-technical readers. Focus on user-visible changes, upgrade impact, supported platforms, and known limitations.
- `changelog-short.txt`: Plain-text version of `changelog-full.md`. Keep the same content, section order, and overall emphasis, but remove Markdown formatting.
- `changelog-full.txt`: Plain-text developer changelog. Include the main shipped changes plus deeper technical detail about subsystems, packaging/build changes, compatibility implications, migration notes, and notable fixes that other developers will care about.

The short changelog pair should be understandable by operators and curious end users. The full changelog can assume the reader knows the codebase and release process.

## Editorial guidance

### What to include

- Breaking changes or compatibility changes that affect operators, packagers, or downstream developers.
- New user-facing capabilities such as launcher, updater, UI, packaging, or configuration behavior.
- Platform-specific installation or upgrade changes.
- Reliability, performance, and security fixes that users can safely understand after disclosure.
- Build or tooling changes only when they matter to contributors, packagers, or reproducible builds.

### What to omit

- Pure refactors with no user-visible effect.
- Fixes for bugs introduced and fixed before any release shipped.
- Raw PR-title dumps or autogenerated `What's Changed` sections left unedited.
- Internal cleanup that does not change shipped artifacts, APIs, or operator workflow.

For `changelog-full.txt`, you may include selected internal details when they help developers understand the release. Keep them out of `changelog-full.md` and `changelog-short.txt` unless they directly affect non-technical readers.

## Recommended section order

Use the sections that fit the release. Omit empty sections.

1. Introduction paragraph
2. `## What's new`
3. `## Upgrade and compatibility`
4. Additional themed sections such as `## Installers and packaging`, `## Launcher`, `## Core updater`, `## Stability and security`
5. `## Known limitations` when needed
6. `## SHA256 checksums` when checksums are published inline

Do not add `Draft`, `Draft status`, or `Reference` sections to changelog artifacts unless the user explicitly asks for them.

For `changelog-full.txt`, it is acceptable to add developer-oriented sections such as:

1. Build and packaging changes
2. Runtime and compatibility notes
3. Developer-facing fixes
4. Subsystem-specific changes

## Formatting conventions

### Introduction paragraph

Start with one or two sentences that summarize the release in plain language. Lead with the biggest operator-facing changes.
When the intro names the release explicitly, use the `v` prefix, for example `Cryptad v2`.

### Entries and bullets

- Start bullet entries with a strong verb: `Add`, `Improve`, `Fix`, `Remove`, `Change`.
- Group related changes under a themed heading instead of listing every merged PR separately.
- Include PR links only when they add traceability or help a contributor follow up.

### Breaking changes

If a release contains a breaking change, put it near the top of `## Upgrade and compatibility` and label it explicitly.

Example:

> Breaking change: the updater now downloads OS packages instead of replacing the core JAR in place.

### Platform notes

Use subsections or tables when Linux, macOS, Windows, Flatpak, or Snap behavior differs in ways that affect installation or upgrades.

### Checksums

If the release includes inline checksums, put them at the end in a fenced `text` block under `## SHA256 checksums`.

### GitHub-specific note

Do not add a `View release on GitHub` link inside a GitHub release body. The page already is the release.

### Plain-text changelog conversion

For `changelog-short.txt` and `changelog-full.txt`:

- Replace Markdown headings with simple plain-text headings.
- Keep bullets as `- ` entries.
- Render code blocks as indented text or fenced plain text if that is clearer.
- Do not leave Markdown links inline; prefer `Label: URL` or just the bare URL.
- `changelog-short.txt` must not add new content beyond what appears in `changelog-full.md`.

## What good Cryptad release notes look like

- They read like a curated explanation, not an export from GitHub automation.
- They connect changes to the real deployment model: integer build tags, platform packages, updater behavior, bundled runtime, and compatibility constraints.
- They tell operators what changed for them, not just what changed in the codebase.
- They keep the short changelog pair non-technical and reserve deeper implementation detail for `changelog-full.txt`.
- They keep pre-tag status out of the changelog files unless the user explicitly asks for it, while still making that status clear in working notes or the final response.

## Evaluation checklist

- [ ] The build number and tag format are correct.
- [ ] If the tag does not exist yet, the pre-tag status is called out outside the changelog artifacts.
- [ ] The introduction highlights the most important shipped changes.
- [ ] Upgrade or compatibility changes are explicit.
- [ ] Platform-specific behavior is called out when it matters.
- [ ] The body does not contain an unedited autogenerated `What's Changed` dump.
- [ ] `changelog-short.txt` matches `changelog-full.md` in content, just without Markdown.
- [ ] `changelog-full.txt` adds useful technical depth without turning into a raw commit dump.

# Trust and social content format profiles

This page defines the Crypta app ecosystem content format profiles used by Profile Publisher, Feed
Reader, Trust Graph Local RC, Social Inbox RC, the browser SDK, and release certification.

These content profiles are Crypta app ecosystem profiles. They are not compatibility promises for
legacy WoT, Freetalk, Sone, Freemail, or any old plugin ABI/protocol.

The profiles are document contracts, not Platform API routes. They are not Platform API 1.0 stable
baseline route guarantees. Platform API compatibility remains governed by
[platform-api-compatibility-support-window.md](platform-api-compatibility-support-window.md).

## Profile table

| Profile | Identifier | Content type | Filename | Status | Max document bytes | Signed | Signing domain or purpose |
| --- | --- | --- | --- | --- | ---: | --- | --- |
| Profile document | `crypta.profile.v1` | `application/vnd.crypta.profile+json` | `profile.json` | experimental | 65536 | yes | `profile.publish.v1` |
| Feed snapshot | `crypta.feed.snapshot.v1` | `application/vnd.crypta.feed+json` | `feed.json` | stable | 65536 | no | n/a |
| Trust statement | `crypta.trust.statement.v1` | `application/vnd.crypta.trust+json` | `trust.json` | experimental | 65536 | yes | `crypta.trust.statement.v1` |
| Social message | `crypta.social.message.v1` | `application/json` | n/a | experimental | 65536 | yes | `crypta.social.message.v1` |
| Social outbox | `crypta.social.outbox.v1` | `application/vnd.crypta.social.outbox+json` | `social-outbox.json` | experimental | 65536 | no | n/a |

Signed profile, trust, and social-message payloads are capped at 32768 canonical UTF-8 bytes before
signing. Feed snapshots and social outboxes share the 65536-byte generated app-document cap so the
profile limit matches the publish route. The generic content-fetch route can have a broader default
for other content, but profile parsers must reject profile documents above the profile limit.

## Version policy

All v1 profiles use a conservative policy:

- unknown fields are rejected for signed and canonical profiles;
- future major versions such as `crypta.social.message.v2` are not treated as v1;
- known deprecated versions produce an explicit `deprecated_version` validation outcome or are
  rejected when the profile policy requires rejection;
- replacement profile metadata is reported when a deprecated profile has a known replacement;
- same-major additive minor behavior can be introduced only by a future profile definition and
  matching parser tests.

Malformed JSON reports `malformed_document`. Documents above the profile byte limit report
`oversized_document`. Unknown or future major versions report `unsupported_version`.
Signature or canonical byte mismatches report a signature or canonicalization mismatch without
echoing the document body or raw signature bytes.

## Canonicalization

Canonical JSON is compact UTF-8 JSON with deterministic object field order chosen by the profile
builder or parser model. Arrays preserve caller-visible order when that order is part of the
document contract.

Profile document signing uses the deterministic JSON object produced by
`ProfileDocumentRequest.payload()`. The signed document root is generated by
`SignedProfileDocumentBuilder`. The canonical payload bytes enter `AppVaultService.useIdentity` under the fixed purpose
`profile.publish.v1`. The actual signed UTF-8 preimage is
`CryptaAppVault:v1:<appId>:<identityId>:profile.publish.v1:<lowercase SHA-256 hex of payload>`.
It is not the newline-domain helper used by trust and social. The signed document root contains public payload and
public verification material only.

Trust statement signing uses this byte sequence:

```text
crypta.trust.statement.v1
<canonical-payload-json>
```

The newline after the domain is part of the signed byte contract. Lifecycle records such as local
deprecation or revocation are stored separately and do not change the public signed payload.

Social message signing uses this byte sequence:

```text
crypta.social.message.v1
<canonical-message-json>
```

The `messageId` is derived from the canonical public message fields without the `messageId` field,
then the final signed document includes the generated `messageId`. Reply and thread references are
bounded `msg-<sha256>` identifiers and do not grant network fetch authority.

Feed snapshots and social outboxes are unsigned. They still use deterministic field order when the
first-party apps generate them, and import code validates the root `type` before rendering or
persisting summaries.

## Field policy

### Profile document

Required payload fields are `schema`, `appId`, `identityId`, and `displayName`. Optional payload
fields are `bio`, `website`, `avatarUri`, `contactUri`, and ordered `tags`. Unknown request
parameters are rejected before signing. `tags` preserve validated order. The signed document root
is generated by the platform builder and must not contain private identity material, seed material,
private keys, vault paths, process tokens, or private insert URIs.

### Feed snapshot

Required generated fields are `type`, `title`, `updatedAt`, and `items`. Import code also accepts
the older `entries` array name and normalizes it to `items`. Items are bounded and may carry a safe
id or URI summary, title, published time, summary, and tags. Source metadata lives under the
bounded `source.uri` and `source.resolvedUri` fields only. Release evidence uses redacted source
summaries or digests instead of raw fetched feed bodies. Unknown root, source, author, or item
fields are rejected, and unsupported versions must not crash Feed Reader.

### Trust statement

Required root fields are `type`, `payload`, and `signature`. The payload contains bounded issuer,
subject, context, score, confidence, reason, tags, `issuedAt`, and optional `expiresAt` fields as
documented in [trust-graph-preview.md](trust-graph-preview.md). Parser and validator code rejects
unknown fields, invalid subject/context values, unbounded text, out-of-range score or confidence,
oversized tags, and invalid timestamps before verification. Import preview reports safe reason
codes for malformed, oversized, unsupported, deprecated, expired, revoked, and unverified
statements.

### Social message

Required root fields are `type`, `message`, and `signature`. Required message fields include
`appId`, `identityId`, `authorFingerprint`, `messageId`, `createdAt`, `channel`, `body`, and
`format=text/plain`. Optional fields include bounded `authorLabel`, `profileUri`, `subject`,
`replyTo`, `recipientFingerprint`, and ordered `tags`. Unsupported fields are rejected before
signing. Signed documents include public verification material only.

### Social outbox

Required generated fields are `type`, `appId`, `generatedAt`, `sourceLabel`, and `messages`.
`profileUri` is optional and bounded. Each message entry must be a bounded signed
`crypta.social.message.v1` document. Imports reject unsupported outbox types, unsupported message
formats, oversized outboxes, malformed message entries, invalid signatures, and future major
versions before Trust Graph score annotations are queried.

## App responsibilities

Apps should use `CryptaPlatform.contentFormats` instead of duplicating strings. UI may display the
profile id, version, content type, default filename, status, and signing domain in a concise
format-profile section. Detailed migration and field rules belong in this document.

Apps must handle these outcomes distinctly:

| Outcome | Expected app behavior |
| --- | --- |
| Malformed document | Reject import or render a safe parse error. |
| Oversized document | Stop processing and report the profile byte limit. |
| Unsupported version | Do not treat the document as a known v1 profile. |
| Deprecated version | Warn or reject according to the profile policy. |
| Signature/canonicalization mismatch | Reject signed content and show a bounded verification error. |

Apps must not persist or emit raw fetched social documents, raw social message bodies, raw profile
documents, raw trust statements, raw feed bodies, raw signatures, raw app-data values, private
insert URIs, private keys, tokens, browser sessions, or absolute local paths in app-data,
diagnostics, release evidence, support bundles, or docs examples.

## Release certification

Release certification records `app-platform.trust-social-content-format-profiles`. The historical deterministic
offline source inspection checks the following claims; it does not itself execute tests:

- registry descriptors exist for all five profiles;
- Java AppVault, queue, content, trust graph, and parser code uses or drift-tests the same
  identifiers, content types, filenames, byte limits, and signing domains;
- the browser SDK mirrors the Java constants through `CryptaPlatform.contentFormats`;
- Profile Publisher, Feed Reader, Trust Graph Local RC, and Social Inbox RC use SDK format
  descriptors and show bounded format-profile UI copy;
- tests cover malformed, oversized, unsupported-version, deprecated-version, unknown-field, and
  signature/canonicalization mismatch behavior;
- production beta and go/no-go summaries include content-format risk;
- evidence and fixtures include digests, statuses, file references, and booleans only, not raw
  fetched content, raw document bodies, raw signatures, private material, or local paths.

Missing or failing content-profile evidence is a production-beta blocker when it indicates signed
or canonical format drift.

## Stable 1.0 freeze and maintenance baseline

The Stable RC freeze records `content-format-profiles.json` and the registry/canonicalization
digests exercised by the product and first-party apps. Stable GA re-authenticates those exact
bytes. A profile id, version, content type, filename, size limit, signing domain, canonicalization
rule, or app binding cannot change between the selected RC and GA authorization.

The post-GA maintenance baseline retains the frozen profile versions and canonicalization digests
for future maintenance and hotfix comparison. If a content-profile defect requires a change before
GA, stop validation and complete a new authorized RC refreeze; do not patch the GA metadata or
waive format drift.

## Non-goals

These profiles do not implement WoT, Freetalk, Sone, Freemail, or old plugin ABI/protocol
compatibility. They do not add global moderation, daemon-core crawling, arbitrary browser signing,
remote scripts, analytics, direct HTTP fetch, or generic network-message storage. They do not
expose AppVault private key material or raw identity envelopes.

## Stable 1.0 maintenance compatibility

Maintenance validation compares all frozen v1 profile identities, descriptor digests,
canonicalization rules, signature payload rules, field meanings, and size semantics against both
the immutable GA baseline and the immediate predecessor. Parser, bounds, diagnostic, and verifier
bug fixes are allowed only when previously valid signed documents remain valid. An incompatible
change requires a separately versioned profile and an explicit migration plan.

See the [Stable 1.0 maintenance release and security hotfix
path](stable-1.0-maintenance-release-and-hotfix-path.md).

## Lifecycle governance projection

Stable lifecycle certification reuses the authenticated profile registry and frozen Stable 1.0
profile identities. The report carries each profile's active/deprecated state, replacement id,
migration guidance, canonicalization digest, signature-payload contract, and version policy. It
does not change signed document bytes or introduce a competing profile authority.

Deprecating a frozen profile requires a separately versioned replacement and explicit migration
policy. A maintenance baseline or lifecycle descriptor cannot change v1 canonicalization,
signature rules, field meanings, or the original deprecation clock in place. See [Stable 1.0 support lifecycle and deprecation governance](stable-1.0-support-lifecycle-and-deprecation-governance.md).

## Executable maturity review

The [stable profile review](trust-social-stable-profile-review.md) adds a shared public synthetic
corpus, production Java and JavaScript execution, strict local result binding, and separate content
and service dispositions. Feed remains stable and four signed/aggregate profiles remain experimental.
Only dedicated test resources may contain the reviewed synthetic documents and public test vectors;
this exception does not relax support/release redaction or permit real user content in evidence.
